# 爬坡 Ramp · 单位经济模型

> 数据来源：本地 MySQL 的 `traces` 表，83 条真实 span，53 次模型调用。
> 单价核对于 2026-08-27，来源 [DeepSeek 官方定价](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)。
> 除特别说明外，所有金额为**空闲时段**价格。

---

## 0. 先说口径，再说数字

一份不交代口径的成本表没有价值。这份文档的四个前提：

1. **金额来自 `traces` 表按 `session_id` 求和**，不是从 state 累加得来的。
   原因见下方「踩过的坑」——state 那条路会把父图节点算两遍。
2. **工具调用成本记为 ¥0**：目前三个外部系统是 mock JSON，没有真实 API 计费。
   真实部署要把外部系统的调用成本单列一行。
3. **不含 embedding 成本**：知识入库时算一次向量（百炼 `text-embedding-v4`），
   之后存在 MySQL 的 JSON 列里，检索时不再调 API。53 条知识的一次性成本可忽略，
   但**知识飞轮每沉淀一条就产生一次 embedding 调用**，规模化后需要单列。
4. **样本小**。53 次模型调用不足以支撑精确的单价预测，只够支撑**结构性结论**——
   哪一类请求贵、贵在哪里、动哪个杠杆有效。

## 1. 单价表

元 / 百万 token。高峰＝北京时间周一至周五 9:00–12:00、14:00–18:00；空闲价是高峰价的一半。

| 模型 | 时段 | 输入·缓存命中 | 输入·未命中 | 输出 |
|---|---|---:|---:|---:|
| `deepseek-v4-flash`（tier2） | 高峰 | 0.10 | 3.00 | 9.00 |
| | 空闲 | 0.05 | 1.50 | 4.50 |
| `deepseek-v4-pro`（tier1） | 高峰 | 0.30 | 9.00 | 27.00 |
| | 空闲 | 0.15 | 4.50 | 13.50 |

**两个结构性事实，直接决定了产品怎么设计：**

- **缓存命中比未命中便宜 30 倍**（flash 高峰 0.10 vs 3.00）
  → 所以 `prompts.build()` 把稳定前缀放最前面。那不是代码洁癖，是省钱。
- **空闲时段是高峰的一半**
  → 所以 `proactive.py` 的节点推送安排在空闲时段跑。

## 4. 缓存命中的真实收益

| 指标 | 实测 |
|---|---:|
| 命中率（按 span 均值） | 49.2% |
| 命中率（按 token 总量） | **48.7%**（27,008 / 55,462） |
| 单次最高命中率 | 99.7% |
| 命中省下的钱 | ¥0.0783 |
| 实际账单 | ¥0.1959 |
| 若全部未命中 | ¥0.2742 |
| **省掉的比例** | **29%** |

分层 prompt 那个「稳定前缀在前」的一行决定，实测省掉了近三成账单。

**这也解释了为什么会话层不能放在最前面**：`## 今天是他入职的第 14 天`
一旦排在系统提示词前面，缓存**每天失效一次**——上面这 29% 会直接消失。

## 6. 最大的那个杠杆：advice 占 5% 的量，占 49% 的钱

这是整份成本分析里唯一真正重要的发现。

`advice` 单次 ¥0.0392，是 L0 的 **39 倍**，平均耗时 **44 秒**。三个原因叠加：

1. 走 **tier1**（单价 3 倍）
2. 输出极长（实测 2,841 token）——`ADVICE_REPLY` 要求「3 条具体可执行的建议」，
   模型理解成了长篇大论
3. **触发了截断自愈重试**——输出撞上 `max_tokens` 后加倍预算重来，等于付两次钱

**改法（按性价比排序）：**

| 动作 | 预期效果 |
|---|---|
| advice 降到 tier2 + 输出上限 800 token | 加权单次 ¥0.0039 → **¥0.0024，总成本降 39%** |
| 给 `ADVICE_REPLY` 加「每条不超过 60 字」的硬约束 | 减少截断重试 |
| 把「建议类」的首轮响应改成先给要点、要展开再展开 | 同时改善 44 秒的等待体验 |

**但要注意这是个取舍，不是纯优化。** advice 用 tier1 是有理由的——它是唯一没有
知识库垫底、完全靠模型判断的路径。降档之前必须先在黄金集的 advice 那 9 条上验证，
确认通过率不掉（当前 8/9）。**先看质量再省钱，顺序反了就是自欺。**

## 7. 定价与 ROI

### 定价结构

**按「入职人次」计费，不按 seat。** 三个理由：

1. 价值随新人数量线性变化，与在职总人数无关
2. HR 预算里「人均入职成本」是现成科目，不需要新开预算
3. 避免客户在招聘淡季质疑 seat 费用

### 毛利结构

模型成本人均 ¥0.48–0.96，**几乎可以忽略**。这带来一个反直觉但重要的结论：

> **B 端 AI 产品真正的成本大头是实施，不是 token。**

真实成本构成：知识库初始化的人力（整理、分级、标注有效期）、
系统对接（HR / IT / 组织架构三方接口）、试点期的运营陪跑。
模型调用连零头都算不上。

在定价上应该把模型成本控制在售价的 15% 以内——但按现在的数字，
就算定价只有几十元一人次，模型成本占比也远低于这个线。**约束不在这里。**

### ROI 算式

```
年化收益 = 年入职人数 × 爬坡期缩短天数 × 人均日成本
         + 年入职人数 × 减少的 mentor 打断次数 × 单次打断成本
```

单次打断成本要含**重新进入专注状态的隐性时间**，通常按 15–25 分钟计。

灰度期对照组存在的唯一目的，就是把这个算式里的每个变量换成客户自己的真实数字。
在那之前，任何 ROI 数字都只是示意。

## 8. 踩过的坑：成本数字被系统性多算

一度所有成本都偏高，原因是 `spans` / `cost` 用了 `operator.add` 累加器，
而 **LangGraph 的子图会继承父图 state 再整体回传**——父图在进子图之前记的
那几条（`classify` / `dispatch`）被加了第二遍。

119 条 span 里 **36 条是重复的**，虚高约 ¥0.0137。

**这个 bug 很隐蔽：它不报错，只是让所有成本数字偏高。**

修法有三层：

1. 每个 span 带 `uid`，累加器换成 `merge_spans` 按 uid 去重
2. 最终成本**从去重后的 spans 派生**，不再单独累加——一个真相来源
3. `trace.persist()` 按 uid 幂等——HITL 那一轮会写两次（`ask()` 一次、
   `resume()` 一次且有重叠）

> 因此：本仓库 `reports/full_run_v4.json` 里的 **¥0.5835 是修复前的数字，偏高**，
> 真实值约 ¥0.54。下一次回归会给出修正后的口径。

## 9. 已知局限

- **样本只有 53 次模型调用**，够支撑结构性结论，不够做精确预测。
- **路由分布是假设不是实测**。真实流量的 advice 占比若高于 5%，成本会显著上升——
  而这恰恰是最可能发生的：新人问的开放性问题往往比制度问题多。
- **工具成本记为零**。真实系统对接后要单列。
- **embedding 成本未计入**。知识飞轮规模化后需要单列。
- **没有并发与重试的真实数据**。生产环境的限流退避会带来额外调用。
