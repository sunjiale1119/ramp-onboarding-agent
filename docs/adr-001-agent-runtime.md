# ADR-001：为什么继续使用 LangGraph

日期：2026-09-10。状态：采用，针对当前小团队试用阶段。

这是一份补充整理的选型记录，不是伪造项目开始前已完成的对照实验。已实际实现并测试 LangGraph 路径；未对 DeepSeek Harness 做同条件原型或性能测试。

## 先从需求出发

Ramp 的任务不是开放式操作电脑，而是按明确边界完成入职问答与申请：区分业务领域；按有效知识版本回答；遇到写操作等待本人确认；重启后恢复；不允许越权；重复确认不能重复建单。当前已有 Python/FastAPI/MySQL 业务层，部署在单机小规格服务器。

DeepSeek 模型回答“用哪个模型推理”，LangGraph 或 Harness 回答“怎样组织运行过程”，数据库事务和服务端权限回答“执行是否可靠、是否合法”。三者不能混为一谈。

## 候选与取舍

| 候选 | 适配与代价 | 本阶段选择 |
|---|---|---|
| LangGraph | 显式状态图、条件路由、interrupt 和持久化恢复与当前确定性审批流程直接对应；已接入 Python 业务层。仍需自己做权限、幂等、数据治理；自维护 MySQL checkpointer 有升级成本。 | 保留，补齐业务保障与回归测试。 |
| DeepSeek Harness | 官方采用插件化 Agent 运行时，可组合模型、工具、会话、存储、调度等能力，并支持运行轨迹与恢复。适合需要高度可扩展运行时的任务；能实现 B 端流程，不应说它“只能写代码”。当前迁移意味着重接业务权限与持久化，且需要验证开发者预览阶段 API 变化的影响。 | 作为候选，不在没有收益证据时重写现有链路。 |
| 模型 SDK + 自写状态机 | 简单单轮问答依赖少，但本项目跨轮等待、恢复、领域分支已复杂，自写会增加状态管理与维护工作。 | 适合作为简单基线，不作为当前替换方案。 |

LangGraph 的暂停和恢复机制见[官方 interrupts 文档](https://docs.langchain.com/oss/python/langgraph/interrupts)。官方同时说明恢复会重新执行暂停节点起点之前的代码；因此我们将写操作放在确认之后，并增加业务操作编号、数据库唯一记录与事务，不能声称“用了框架就自动只执行一次”。

DeepSeek Harness 的能力与开发者预览状态依据其[官方介绍](https://www.deepseek.com/harness/)与[官方仓库](https://github.com/deepseek-ai/deepseek-harness)，核对日期为本文日期。上述迁移成本是基于本项目技术栈的判断，不是它性能更差的实测结论。

## 选型怎样验证

当前已经验证：知识草稿不进入检索；并发发布发生冲突时拒绝；别人不能恢复我的会话；确认前不创建工单；重复确认只返回同一工单；重新创建执行图与 MySQL saver 后仍能恢复已保存的暂停状态。

如果未来对 Harness 做原型，使用同一套上述业务案例，加上日志脱敏、故障后查询、运行成本、迁移代码量和依赖升级成本；先规定验收条件，再测量。当前没有双框架的延迟/费用/成功率对照表，不虚构打分。

## 面试时可以这样说

“最开始我按场景适配选择了 LangGraph，但确实没有完成全面框架对照，这是不足。后来我把选型补成了需求和验证清单：我们的核心不是让 Agent 自由操作，而是让入职流程可控，写入前必须确认、中断后能恢复，所以显式状态图很合适。DeepSeek Harness 也是合理候选，强项是可组合的插件运行时，并不是不能做这个场景；但换框架仍要重做业务对接，不能自动解决权限和重复提交。我现在用实际故障与越权测试证明现有方案，后续再用同一组案例做替代方案验证，而不是为了追新框架重写。”
