# 知识版本管理与冲突审核

## 如何使用

管理员登录后进入「管理后台 → 知识库」。修改制度时，先找到原条款，点击「基于此版修改」，不要把它作为另一条独立制度重复上传。

1. 修改内容、来源、生效日期，填写变更说明，点击「保存草稿」。原版本继续用于回答。
2. 查看自动展示的新旧差异和相似条款。核对原制度、适用范围、日期，填写审核意见。
3. 勾选审核确认，点击「审核通过并发布」。今天生效的版本用于后续检索；未来生效的版本到指定日期才被检索。
4. 在「按日期预览检索结果」输入问题、日期和团队，检查实际选中的知识及版本引用。新人工作台也提供制度适用日期选项，默认今天。
5. 「版本历史」保留发布人、变更说明和操作记录。恢复旧内容会创建新草稿，须重新审核发布；不会覆盖历史。

支持粘贴文本或导入 TXT / Markdown（单文件小于 100 KB、内容不超过 20,000 字）。当前按条款维护，不是整本 PDF / Word 自动拆分解析。

## 例子

同一个「差旅住宿报销上限」条款，v1 为 500 元，v2 改成 600 元并在明天生效：

- v2 是草稿：今天、明天都不能用草稿回答。
- v2 审核发布但未到生效日：今天仍使用 v1。
- 明天起：使用 v2，不把两个版本一起发给模型。
- 查询今天的历史制度：选择今天的日期，仍可查到 v1。
- v2 后来失效：不自动恢复 v1。需要管理员恢复旧内容为新版本，或发布后续制度。

## 冲突规则

| 情况 | 处理 |
| --- | --- |
| 同一条款更新 | 独立版本号、内容快照；新版按生效日期替代旧版 |
| 不同条款，同领域、同规则主题，日期和适用团队重叠 | 硬拦截，不允许勾选强行发布；应基于原条款更新，或明确不同规则与范围 |
| 不同主题但问题文本相似，日期和范围重叠 | 提示候选条款及全文，要求逐条确认并填写审核理由 |
| 同一规则仅适用于不同的具体团队 | 可以并存；检索前按新人账号配置的团队过滤 |
| 全公司规则与某团队同主题规则重叠 | 视为冲突，不暗设“部门规则优先” |
| 审核之后别人发布了新知识，或修改了草稿 | 审核凭证过期，必须重新检查 |
| 两人基于同一旧版分别起草 | 后发布者必须基于最新发布版重新起草，不能静默覆盖 |

相似度使用规范化问题文本的 `SequenceMatcher`，阈值 0.45，仅用于提示，不代表已判定语义矛盾。规则主题由管理员维护；同义主题、跨条款逻辑矛盾等仍可能漏检。旧数据迁移不自动判断全部历史语义冲突，也不代表旧知识已经重新审核。

## 数据与检索实现

- `knowledge` 保存每个版本各自的内容和向量；已发布内容不允许原地修改。
- `kb_versions` 保存条款 ID、递增版本号、草稿来源、状态、适用团队、生效内容关联、创建人及审核人。
- `kb_audit` 记录草稿创建、修改、发布、撤回、恢复动作及快照。它是应用级留痕，不是防数据库管理员篡改的合规审计系统。
- `kb_catalog` 的单行锁在 MySQL 上串行化生命周期写操作；草稿 `revision` 防止旧页面覆盖新修改，审核凭证绑定内容、版本、日期和目录代数。
- 发布事务同时写入向量、发布状态、审计和目录代数；向量生成失败时事务回滚，旧版仍可用。
- 检索前只选择已发布、指定日期有效且适用团队匹配的版本。旧版有效区间截到新版生效前一天，日期包含首尾当天。
- 每次获取索引时检查数据库目录代数，并按日期、团队隔离索引缓存。发布后其他进程的下一次检索会重建索引；日期变化也触发重新选择版本。已在执行的回答不会被撤回重算。
- 引用包含来源、发布确认人、条款短 ID、版本号、适用范围。检索 trace 保存本次日期和命中的引用。
- Mentor 提交的可复用回答也先成为草稿；管理员发布后才进入检索，不存在旁路直接写入有效知识。审核状态同步回升级卡片。

## 上线和回退注意

先备份数据库，再使用相同环境配置运行：

```sh
python -m ramp.migrate_knowledge
```

迁移新增三张表，把已有知识关联为已发布 v1，保留内容和原始日期；重复运行不会重复生成版本。应用启动也执行该幂等迁移。请先完成一次迁移，再启动多实例。

“今天”按应用服务器的本地日期解释，生产应统一使用 `Asia/Shanghai` 时区；审计时间为 UTC。当前时间粒度为天，不支持同一天按小时切换。

发布后不要直接回退到不支持版本过滤的旧程序：旧程序会读取 `knowledge` 中的草稿和历史内容。业务回退应使用“恢复历史内容为新草稿”功能；代码回退必须保持版本过滤逻辑，或停止服务并用完整备份恢复到升级前状态。

这些测试不等于完整生产验收：本轮没有重新运行付费大模型黄金集，没有执行真实 MySQL 多进程压力测试，也没有验证 PDF 解析或全量语义冲突识别。现有同一管理员可起草并审核，尚未要求双人分权。历史聊天已加上不可作为制度依据的约束，但尚无独立的历史答案撤回机制。
